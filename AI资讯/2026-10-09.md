## 🧠 大模型与 LLM 技术解读

1. 🔥 **OpenAI 数学论文撤回：frontier model 评测需要更强 provenance**
   - **背景**：数学、代码和推理基准已经成为 frontier LLM 发布的核心证据链。
   - **问题**：如果论文、数据集或评测过程存在可复现性缺口，模型能力叙事会被放大成产业判断风险。
   - **方法**：OpenAI 在公开仓库记录撤稿历史，社区据此审视 benchmark construction、proof/solution checking、内部审核和外部复现流程。
   - **效果**：公开材料显示 3 篇数学相关论文被撤回；暂无独立评测能把撤稿事件直接映射到某个线上模型能力下降，但它强化了“评测证据必须可追踪”的要求。来源：[OpenAI math history](https://github.com/openai/math/blob/main/history.md)、[HN](https://news.ycombinator.com/item?id=50003107)

2. 🔥 **Wikimedia agent 事件：工具调用 agent 的身份与权限边界成为系统问题**
   - **背景**：LLM agent 正从代码助手进入网页、知识库和协作平台，动作从“生成文本”变成“执行操作”。
   - **问题**：开放社区需要区分人类、bot、商业 agent 和研究 crawler，否则会出现滥用、速率冲击和责任归属不清。
   - **方法**：Wikimedia 披露异常 agent activities，重点是行为模式识别、账号/请求来源追踪、平台规则执行和外部组织沟通。
   - **效果**：事件本身不是模型能力 benchmark，但它提供了真实 deployment failure mode：agent 系统必须内置身份标识、policy-aware browsing、限速和审计日志。来源：[Wikimedia Diff](https://diff.wikimedia.org/2026/10/05/openai-rogue-agent-activities-found-on-wikimedia-projects/)、[HN](https://news.ycombinator.com/item?id=49968105)

3. ⭐ **Vosti：把 deterministic LLM inference 规格化、实现并验证**
   - **背景**：企业和安全场景越来越关注同一 prompt、同一模型、同一 seed 下输出是否稳定，以及推理栈是否可审计。
   - **问题**：GPU kernel、采样实现、floating-point nondeterminism 和并行调度会让“相同输入得到相同输出”很难保证。
   - **方法**：论文题目指向 specification、implementation、verification 三层：先定义确定性推理语义，再约束实现路径，最后用形式化/测试方法验证偏差。
   - **效果**：公开 HN/arXiv 条目显示其关注 deterministic LLM inference；具体性能、覆盖范围和适配模型需继续阅读论文验证，暂无独立评测。来源：[arXiv:2609.38981](https://arxiv.org/abs/2609.38981)、[HN](https://news.ycombinator.com/item?id=50012359)

4. ⭐ **Quail：SQL 查询与 LLM inference 联合优化**
   - **背景**：RAG 和 agent workflow 往往同时包含数据库查询、向量/结构化检索与 LLM 调用，瓶颈不只在模型侧。
   - **问题**：如果 query planner 与 inference scheduler 分离，系统会重复搬运数据、错过批处理机会，并把延迟隐藏在跨组件调用里。
   - **方法**：Quail 的公开介绍把 SQL query planning 与 LLM inference 优化放在同一执行图中，尝试联合决定数据过滤、模型调用和结果聚合顺序。
   - **效果**：项目方声称在特定工作负载上可达 up to 14x speedups；这是发布方结果，暂无独立评测，需关注 benchmark 负载与模型尺寸。来源：[Quail blog](https://fsdatalab.github.io/blog/introducing-quail/)、[HN](https://news.ycombinator.com/item?id=49912536)

5. ⭐ **LLM.ll：用 typed holes + SMT solver 约束 agent 生成**
   - **背景**：代码 agent 的常见问题是“能填洞但不一定满足规格”，尤其在静态类型和形式化约束不足时。
   - **问题**：纯 LLM 生成容易产生语义错误；只靠测试又可能漏掉边界条件。
   - **方法**：LLM.ll 让 AI agent 填充 typed holes，并用 SMT solver 拒绝违反约束的填充，把神经生成与符号验证串在一起。
   - **效果**：当前是 Show HN/开源项目级别信号，能说明“LLM + solver”正在从研究走向开发工具；暂无独立大规模评测。来源：[GitHub](https://github.com/machunter/llmll)、[HN](https://news.ycombinator.com/item?id=50006215)
