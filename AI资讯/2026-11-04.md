## 🧠 大模型与 LLM 技术解读

### 1. ⭐ LifeVal：评测 Agent 的“办事”能力

- **背景**：通用助手从问答走向浏览器、computer use 和连接器工作流。
- **问题**：知识题得分无法直接反映个人事务是否被可靠完成。
- **方法**：OpenAI 从时间使用调查建任务分类，并用 3,995 人调查选择高需求场景，构造日常事务评测。
- **效果**：官方展示部分任务表现；公开页不足以独立复算总体成功率，且暂无独立评测。
- 来源：[原始来源](https://openai.com/index/lifeval/)

### 2. ⭐ Flide：精确复用分支状态

- **背景**：决策型 Agent 在许多候选分支上共享推理前缀。
- **问题**：逐分支执行重复计算；近似缓存又可能改变结果。
- **方法**：论文把逻辑树线性化成 token 流，以 GPU 索引和 ForkAttention 管理标准注意力与 Gated DeltaNet 的状态。
- **效果**：作者报告最高 9.5 倍查询加速；该结果限于论文负载，暂无独立评测。
- 来源：[arXiv](https://arxiv.org/abs/2610.42148)

### 3. ⭐ DecisionRank：把重排从生成改为打分

- **背景**：检索增强生成常需在长候选列表上重排。
- **问题**：逐 token 生成文档 ID 带来解码延迟，教师与学生目标空间也不一致。
- **方法**：item-space on-policy distillation 以学生排序形成序列，再接收生成式教师的条件反馈，结合离线监督训练。
- **效果**：作者在 TREC DL、BRIGHT 报告 8B 版本相对其生成式对照更快；不等同于全部检索系统的端到端收益，暂无独立评测。
- 来源：[arXiv](https://arxiv.org/abs/2610.42128)

### 4. ⭐ ZHA：让稀疏注意力的索引也避开二次增长

- **背景**：长上下文成本不只来自 KV 存储，也来自选取稀疏 KV 的索引计算。
- **问题**：若索引仍为二次复杂度，稀疏 attention 无法根治长度扩张。
- **方法**：递归压缩 key 摘要成树，query 自顶向下选择 key，并用短程 KL 蒸馏适配预训练模型。
- **效果**：作者给出多任务实验与超长上下文建模；不应把性能建模说成部署规模，暂无独立评测。
- 来源：[arXiv](https://arxiv.org/abs/2610.42112)
