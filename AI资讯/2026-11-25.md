## 🧠 大模型与 LLM 技术解读

### 1. 🔥 GPT-6.2 Astra / Sol：将能力—成本—计算机操作拆为可路由产品层

- **背景**：企业 Agent 同时存在高难 reasoning/coding 与高频工具调用，单一旗舰模型难以同时优化能力、响应时间和成本。
- **问题**：没有清晰的模型分层时，团队难把复杂任务、computer use 权限和预算约束可靠地编排进同一个工作流。
- **方法**：OpenAI 发布 Astra 与 Sol，并在产品页中将改进点覆盖到 professional output、coding、computer use 与效率；实际接入仍应以 API 文档、模型卡和内部评测确认可用能力。
- **效果**：这是发布方的产品定位，并非统一外部基准结论；公开页面未提供可用于跨厂商复现的完整业务负载比较，暂无独立评测。[OpenAI 发布页](https://openai.com/news/product-releases/) · [GPT-6.2 system card](https://deploymentsafety.openai.com/gpt-6-2-chatgpt/gpt-6-2-chatgpt.pdf)

### 2. ⭐ Hidden-State Refinement：diffusion language model 不只在 token 上迭代

- **背景**：Masked diffusion language model（MDLM）以多步去噪生成文本，天然保留每层、每步的连续 hidden states。
- **问题**：若只保留 token 层预测，跨去噪步的表示演化被丢弃，可能限制并行去噪文本生成的质量。
- **方法**：论文提出 Cross-Step Recurrent Refinement（CSRR），将跨步 hidden-state 信息传递到后续去噪步骤，并分析层内与跨步的表示细化现象。
- **效果**：作者报告 CSRR 改善文本生成质量；该结论来自论文实验，尚无独立复现，且需进一步核查模型规模、推理步数和计算开销。[arXiv](https://arxiv.org/abs/2611.32416)

### 3. ⭐ CPU-Eval：用真实 CPU RTL 拉开 LLM 硬件代码生成差距

- **背景**：VerilogEval 等基准上高通过率可能掩盖实际 CPU 开发中的复杂性，尤其与 ASIC/数字设计工作流相关。
- **问题**：通用 HDL 小题无法充分测到跨模块规模、不同 HDL 语言及真实设计约束下的 LLM 代码生成可靠性。
- **方法**：CPU-Eval 从六个 CPU 设计构建 339 个 HDL 生成题，覆盖 SystemVerilog、Chisel 与 SpinalHDL，并比较七个 LLM。
- **效果**：作者报告模型平均 pass@1 比 VerilogEval v2 Spec-to-RTL 低 45.14 个百分点；这是作者基准结果，未替代具体项目的 lint、formal、仿真与人工 sign-off。[arXiv](https://arxiv.org/abs/2611.32405)

### 4. 📌 Agent time-horizon 评测：单条成功率曲线未必能识别“任务越久越稳”

- **背景**：前沿 Agent 常以 task-completion probability 与人类完成时长的关系评估可自主工作的时间跨度。
- **问题**：仅凭横截面 time-horizon curve 推断任务内失败 hazard 的方向，可能存在统计不可识别性。
- **方法**：论文分析 log-logistic 曲线与 frailty model，并提出借助同一任务的重复运行来恢复部分识别；同时在 METR 公开运行数据上作条件性检验。
- **效果**：作者指出结果依赖模型假设与人类工时获取方式；这提示采购/评测团队应保存重复运行、失败模式和批次信息，而非只引用单一 horizon 数字。[arXiv](https://arxiv.org/abs/2611.32415)
