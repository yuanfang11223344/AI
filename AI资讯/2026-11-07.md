## 🧠 大模型与 LLM 技术解读

### 🔥 Codex 的代码资产层扩展（Pierre 收购）

- **背景：** 编程 Agent 从“生成补丁”转向跨仓库理解、审查与持续协作，代码存储和变更上下文成为能力上限的一部分。
- **问题：** 仅凭单轮上下文很难可靠处理历史、依赖关系、评审流程与权限受控的代码资产。
- **方法：** OpenAI 公告称将收购 Pierre，并把其代码存储能力扩展到 Codex 的构建、理解和审查工具中；公告未披露检索索引、权限模型或推理架构细节。
- **效果：** 属于产品整合计划，暂无公开的独立效果评测或迁移成功率数据。
- **来源：** [OpenAI 新闻页](https://openai.com/news/company-announcements/?display=list)

### ⭐ GPT-6.1 Terra：面向规模化 computer use 的产品定位

- **背景：** Agent 使用 GUI、浏览器和本地工具时，需要把视觉理解、规划、执行与安全限制组合起来。
- **问题：** computer use 的失败常来自界面状态变化、长链路任务累积误差及敏感操作授权。
- **方法：** OpenAI 产品页将 GPT-6.1 Terra 定位为“fast and capable computer use at scale”；目前新闻索引未给出可复核的模型结构、训练数据或端到端基准配置。
- **效果：** 官方作出能力定位，但没有在该索引页提供独立评测；应以任务集、环境版本和人工接管率验证。
- **来源：** [OpenAI Newsroom](https://openai.com/news/company-announcements/?display=list)

### ⭐ 外部红队/评估访问成为前沿模型治理工程的一环

- **背景：** 高能力 LLM 的安全主张需要部署前与部署后的可审计证据，而不只是内部 policy 文档。
- **问题：** 内部评估可能受覆盖范围、利益相关与访问权限限制，难以发现长程 Agent 的失控路径。
- **方法：** Anthropic 表示向 METR 提供更深访问以评估系统；OpenAI 则描述上线前能力/风险评估、滥用监测与分层防护。两者都是流程机制，并非模型算法细节。
- **效果：** 这些安排提高可审计性，但“是否降低真实事故率”仍需独立研究和长期披露；暂无独立因果评测。
- **来源：** [Anthropic](https://www.anthropic.com/news?subjects=announcements)｜[OpenAI](https://openai.com/index/broad-access-through-consistent-standards/)

### ⭐ SafetyID 与跨服务安全执行的身份最小化思路

- **背景：** 模型路由、API 网关与转售使安全执行跨越多个服务主体。
- **问题：** 平台需要在调查滥用时区分终端用户，同时避免让上游模型方获得不必要的身份信息。
- **方法：** OpenAI 说明 SafetyIDs 用于在调查中区分个体而不学习其真实身份，并要求直接提供模型访问的路由/网关接受审查。这是访问控制和运营设计，不是新的模型能力。
- **效果：** 官方预期可更精细地处置风险、减少误伤；隐私与有效性需由外部审计验证，暂无独立评测。
- **来源：** [OpenAI](https://openai.com/index/broad-access-through-consistent-standards/)

### 📌 SwarmEvolve：用潜在 Agent swarm 做演化发现

- **背景：** 多 Agent 搜索被用于把语言模型的生成能力转为候选方案探索。
- **问题：** 直接让 Agent 在大搜索空间中反复交互，成本高且容易缺乏可比较的优化信号。
- **方法：** 论文题目与摘要将方案概括为“Latent Agent Swarms for Evolutionary Discovery and Optimization”；需要阅读正文确认 latent 表示、奖励设计及基线。
- **效果：** 当前为 arXiv 预印本，结论应以作者实验为准，暂无独立复现。
- **来源：** [arXiv:2611.08483](https://arxiv.org/abs/2611.08483)

### 📌 强到弱监督与 GRPO 的算力效率分析

- **背景：** Reasoning/post-training 会消耗大量采样和优化算力。
- **问题：** 强模型生成的监督信号是否能以较低成本迁移给弱模型，取决于训练策略和计算预算。
- **方法：** 该预印本比较 Strong-to-Weak OPD 与 GRPO 的 compute efficiency；标题不足以推断具体优劣，需以论文的 FLOPs、数据与评测设置解读。
- **效果：** 属于作者报告的实验性分析，暂无独立评测。
- **来源：** [arXiv:2611.08453](https://arxiv.org/abs/2611.08453)

## 🖥️ 芯片与互连

- 🔥 **CPO/NPO 的工程动机仍是缩短高速电链路。** Qualcomm 路线图将同封装 die-to-die、PAM4 和光 SerDes 按毫米到公里尺度排布；这说明系统设计应先按 reach、功耗、可维护性与封装热预算选层，不能把 CPO 当作所有场景的默认替代。[来源：Qualcomm](https://www.qualcomm.com/content/dam/qcomm-martech/dm-assets/documents/Investor-Day-2026_TPialis_Data-Center.pdf)
- ⭐ **224Gbps Quad TIA 面向 800G/1.6T 光收发模块。** Coherent 的 OFC 页面列出该器件与下一代 AI/cloud infrastructure 的目标。厂商页面没有给出全链路 BER、温度范围或互操作性数据，部署可行性仍需模块与系统级验证。[来源：Coherent](https://www.coherent.com/events/ofc)
- ⭐ **224G PAM4 到 400G/λ 的硅有机器件路线。** 预印本报告 1.6T-DR8 PIC 的 224G PAM4 open-eye 传输，并讨论 >110GHz 变体；这是实验演示，不能直接外推为量产收发器指标。[来源：arXiv](https://arxiv.org/abs/2509.24825)
- ⭐ **硅微环调制器的 400Gbps/λ 报告值得关注。** 作者称在特定实验条件下取得 200G NRZ、360G PAM4 和 400G PAM6 open eye，并给出能耗陈述；需要留意器件驱动、链路预算和 FEC 假设。[来源：arXiv](https://arxiv.org/abs/2509.01555)
- 📌 **1.8Tb/s/λ/s 多维硅光引擎强调单芯片集成。** 论文把收发器、空间/偏振复用和光信号处理单片整合，目标是减少离散器件和 DSP 负担；截至目前这是研究结果，非商用部署公告。[来源：arXiv](https://arxiv.org/abs/2608.11639)
