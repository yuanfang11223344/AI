## 🧠 大模型与 LLM 技术解读

### 1. Tencent Hy4：把“开放”与可审计性拆开看

- **背景**：开源/开放权重模型正从通用问答转向金融研究、代码与工具调用等高价值 Agent 工作流。
- **问题**：仅给出营销排名难以判断模型是否能稳定完成长链路任务，也无法比较推理成本、数据治理与安全边界。
- **方法**：Tencent 将 Hy4 定位为新一代 LLM，并披露在 iRaB（Investment Research Agent Benchmark）上相对 Preview 的内部增幅；公告还提到向既有产品整合。
- **效果**：公告称 iRaB 增加 12.03 个百分点；该数字来自金融 AI 公司 Rabyte 的内部评测描述，尚缺完整权重、system card、评测协议与独立复现，**暂无独立评测**。[来源](https://www.tencent.com/tencent-launches-hy4-joining-the-ranks-of-the-worlds-leading-open-source-ai-models/)

### 2. METR 参与的前沿系统评估：从静态 benchmark 到能力边界测试

- **背景**：Agent 可以调用工具、执行代码和访问企业数据，单一离线 benchmark 无法覆盖真实权限链路。
- **问题**：如何在不泄露敏感模型细节的前提下，让外部研究者检查自主性、网络操作与高风险能力。
- **方法**：Anthropic 表示向 METR 提供接近员工级访问，并讨论与其他机构合作；重点是评估过程与访问治理，而不是发布新的模型架构。
- **效果**：该机制能增加独立审查入口，但尚未形成公开、可横向比较的评测结果；**暂无独立评测结论**，不应据此推断任一模型的安全等级。[来源](https://www.anthropic.com/news)

### 3. Agent 的科学任务评测：结果分数之外需要过程证据

- **背景**：科研 Agent 正从文献检索扩展到实验规划、仪器/软件交互和结果记录。
- **问题**：自然语言答案正确并不等于实验过程安全、可复现或满足实验室 SOP。
- **方法**：OpenAI 的公开文章讨论对日常 wet-lab 任务中 Agent 行为进行度量；可把任务分解、工具轨迹、人工监督和失败恢复视作评测对象。
- **效果**：这为“Agent 能做什么”提供任务化观察窗口，但公开页面不是通用安全认证，也不构成所有实验环境的部署证明；**暂无独立评测**。[来源](https://openai.com/index/measuring-how-ai-agents-handle-wet-lab-science/)

### 4. `robots.txt` 训练选择：数据治理正在进入模型工程约束

- **背景**：LLM 训练和检索 Agent 都依赖公开网页，站点所有者希望区分搜索索引、实时访问和训练使用。
- **问题**：现有爬虫约定不天然提供统一、可验证的“禁止用于训练”语义，也难以证明所有下游数据管线都遵守。
- **方法**：报道显示 OpenAI、Google、Microsoft、Anthropic 支持以机器可读方式表达 AI 抓取选择；它是生态约定而非模型算法创新。
- **效果**：若获得广泛实现，可降低站点声明成本；但实际覆盖、历史语料处理与第三方执行尚无统一独立审计，**暂无独立评测**。[来源](https://www.techradar.com/ai-platforms-assistants/we-believe-this-is-a-practical-step-toward-an-open-web-dont-want-ai-companies-training-on-your-website-openai-google-and-microsoft-are-backing-a-new-way-to-opt-out)

### 5. MCP server 月度版本：工具调用接口依赖版本化治理

- **背景**：MCP 把模型、客户端和外部工具连接起来，已成为 Agent 工具链的常用接口层。
- **问题**：工具协议/服务器升级会改变输入输出与权限面；无版本锁定会让可复现性和安全审计变差。
- **方法**：`modelcontextprotocol/servers` 的 releases 按 CalVer 发布，例如 `mcp-server-fetch` 的 2026.11.4 条目，便于使用方锁定版本并审查变更。
- **效果**：版本化本身不证明工具正确或安全，但让依赖追踪与回滚可执行；功能和安全效果仍应由部署方测试，**暂无独立评测**。[发布记录](https://github.com/modelcontextprotocol/servers/releases)

## 🖥️ 芯片与互连

- 🔥 **CPO 的接口 IP 正在走向“光引擎 + 224G SerDes + chiplet”协同**：Lightmatter 与 Synopsys 的合作目标是将 3nm 的 224G SerDes 与 UCIe IP 集成到 Passage 3D CPO 平台。公告描述的是联合开发路线，不是量产出货或端到端能效的独立证明。[Lightmatter 公告](https://lightmatter.co/press-release/lightmatter-collaborates-with-synopsys-to-integrate-advanced-interface-ip-with-its-passage-co-packaged-optics-platform/)
- ⭐ **224G/448G 连接正按距离分层**：Qualcomm 数据中心材料把 die-to-die、PAM4 electrical/optical SerDes、CPO/NPO、AEC 与 coherent-lite 排列在毫米到数十公里的尺度上。它提示系统设计不能只比较每 lane 速率，封装、可维修性和链路预算同样关键。[Qualcomm Investor Day 材料](https://www.qualcomm.com/content/dam/qcomm-martech/dm-assets/documents/Investor-Day-2026_TPialis_Data-Center.pdf)
- ⭐ **224G 仍是从电域走向近封装光学的过渡节点**：Huawei Research 将 112G/224G 时代的 LR SerDes、定制 chip-to-chip 互连、LPO/NPO/OBO/CPO 并列讨论，反映了电互连损耗与功耗共同驱动光学靠近封装。[Huawei Research Issue 9](https://www-file.huawei.com/admin/asset/v1/pro/view/1f6f46557899427b9d6b37f0862a550d.pdf)
- 📌 **400G/λ 硅光调制器论文提供器件侧上限参考**：论文报告硅微环在实验条件下实现 200Gb/s NRZ、360Gb/s PAM4 和 400Gb/s PAM6 开眼图；这是器件研究结果，不等同于完整交换机/CPO 产品吞吐。[arXiv:2509.01555](https://arxiv.org/abs/2509.01555)
- 📌 **从 1.6T 到 3.2T 的 PIC 路线仍受调制器带宽约束**：另一项论文报告 224G PAM4 与面向 400G/λ 的 silicon-organic hybrid PIC 结果，为 CPO 光引擎的每波长速率提供实验参照。[arXiv:2509.24825](https://arxiv.org/abs/2509.24825)
