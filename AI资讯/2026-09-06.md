## 🧠 大模型与 LLM 技术解读

1. 🔥 GPT-5 / agentic coding 产品线
   - 背景：商业 LLM 正在从聊天产品转向可调用工具、读写代码库、执行长任务的 agent 系统。
   - 问题：真实工程任务需要跨文件上下文、可恢复状态、工具权限控制和可审计执行；单轮生成代码的能力不足以支撑生产部署。
   - 方法：OpenAI 公开材料强调面向开发者的 API、agentic coding 与工具生态，但关键训练数据、完整系统架构和部署侧隔离策略仍需结合官方文档与产品限制逐项验证。
   - 效果：官方材料显示方向已从模型能力展示转向任务执行；独立评测仍需区分模型本体、工具链、上下文策略和沙箱环境，暂无可一概而论的独立评测。来源：[OpenAI News](https://openai.com/news/)、[OpenAI Developers](https://developers.openai.com/)
2. 🔥 Claude Code 与 coding agent 工作流
   - 背景：Claude Code、Codex 类工具把 LLM 放进代码仓库和终端环境，正在改变软件工程的操作界面。
   - 问题：agent 在本地执行命令、修改文件、读取上下文时，会同时带来效率提升和供应链/权限风险。
   - 方法：Anthropic 文档把 Claude Code 定位为命令行 coding agent，围绕项目上下文、工具调用和开发者交互构建工作流；企业使用时还需额外设置 sandbox、审计和仓库信任边界。
   - 效果：公开资料说明其适合长任务与代码库协作，但具体生产收益强依赖代码库规模、测试质量和权限策略，暂无统一独立评测。来源：[Claude Code Docs](https://docs.anthropic.com/en/docs/claude-code/overview)、[Anthropic News](https://www.anthropic.com/news)
3. ⭐ Gemini API / 多模态模型产品化
   - 背景：Gemini 系列继续作为 Google 多模态和长上下文 AI 应用的核心入口。
   - 问题：企业应用需要在文本、图像、音频、视频、代码和工具调用之间统一接口，同时控制延迟和成本。
   - 方法：Google 通过 Gemini API 提供多模态输入、结构化输出、工具调用和批处理等能力；模型细节通过文档和 model card 分层披露。
   - 效果：官方文档覆盖能力面较广，但公开页面不足以证明所有垂直场景优于竞品；关键仍是第三方任务评测和真实成本曲线。来源：[Gemini API Docs](https://ai.google.dev/gemini-api/docs)、[Google DeepMind Models](https://deepmind.google/models/)
4. ⭐ WeatherNext / AI for Science 模型路线
   - 背景：AI weather model 是深度学习进入科学计算和高价值预测系统的代表方向。
   - 问题：传统数值天气预报计算成本高，概率预报和高分辨率多变量预测需要更快的 ensemble 生成能力。
   - 方法：Google DeepMind 的 WeatherNext 路线用机器学习模型学习历史观测/再分析数据中的时空规律，服务全球天气预测和不确定性估计。
   - 效果：官方材料强调 AI 天气模型的速度和预测能力；不同区域、极端天气和长期稳定性仍需要与 ECMWF/NOAA 等基线持续对比。来源：[Google DeepMind WeatherNext](https://deepmind.google/science/weathernext/)、[Google DeepMind Blog](https://deepmind.google/discover/blog/)
5. ⭐ Speculative Macro Commit for Faster Tool-Using Agents
   - 背景：工具型 agent 的端到端延迟常由 action-observation 串行链路决定，不只是模型 token/s。
   - 问题：coding、browser 和 workflow agent 每一步都等待环境反馈，会造成 wall-clock latency 放大。
   - 方法：论文提出 speculative macro commit，把可预测的多步动作组合成更大的提交单元，并在反馈到来后校正。
   - 效果：摘要声称目标是降低工具型 agent 的串行延迟；具体收益取决于任务可预测性和回滚成本，不应外推到所有 agent。来源：[arXiv:2609.03236](https://arxiv.org/abs/2609.03236)
6. ⭐ R2Adapter: Routing and Rewriting Adapter for Efficient Hybrid RAG
   - 背景：RAG 已成为企业 LLM 补充私有知识的默认模式，但 pipeline 越复杂越容易增加成本与噪声。
   - 问题：不是所有查询都需要检索，同一查询也可能需要不同粒度的 rewrite 与 routing。
   - 方法：论文提出 routing + rewriting adapter，在查询级判断是否检索、如何改写，并服务 hybrid RAG。
   - 效果：摘要显示目标是提高 hybrid RAG 效率；是否能跨数据集稳定提升仍需看完整实验与复现。来源：[arXiv:2609.02894](https://arxiv.org/abs/2609.02894)
